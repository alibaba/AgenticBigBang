# Stage 1: 论文画像

本阶段的任务：仔细阅读 `material.pdf`，生成一个 JSON 对象——
*Paper Card*——包含下游阶段写出高质量任务案例所需的所有信息。
本阶段不写其他文件。你生成的 Paper Card 是后续阶段**唯一能看到的
数据源**。

## 本阶段可用的输入

- 工作目录中的 `material.pdf`。
- 工作目录中的 JSON Schema 文件 `paper_card.schema.json`；你的
  最终 JSON 必须通过其校验。
- 可选的 `_hint.txt` 文件，含论文文件名和从中提取的 ID。仅作为
  标题的弱先验参考；以 PDF 内容为准。

你没有其他读取权限。不要搜索网络。不要推断 PDF 中找不到的元数据。

## 强制阅读流程

即使你认为可以跳过，也必须执行。跳步是任务合成质量低下的首要原因。

1. **Pass A — 结构概览。** 阅读 `material.pdf` 第 1-2 页（标题页 +
   摘要 + 引言）。记录：精确标题、完整作者列表（如标注等同贡献则
   保留标记）、主要单位、摘要全文。如果摘要使用结构化标记
  （【目的】【方法】【结果】【结论】或类似格式），逐段落分别记录。
2. **Pass B — 正文与图表。** 用一次大范围 Read 调用阅读完整正文
  （例如 `pages: "3-N"`，N 为最后一页非参考文献页）。记录每个
   图/表的编号（使用论文原文形式：'图1'/'Fig. 1'/'Figure 1' 或
   '表2'/'Table 2'，如论文中中英文标签共存则以中文形式为主要 id，
   英文形式作备注）、所在页码、展示内容和标题文字。记录摘要、
   结果章节和汇总表中的精确数值结果。
3. **Pass C — 值得检查的细节。** 再次扫描：定义的术语（缩写词、
   命名的模块/方法/指标）、论文对先前工作的方法论区分（例如
   "预混合燃烧 vs 扩散燃烧"、"间伐 vs 皆伐"）、非单调趋势或
   最优点（剂量响应曲线、参数甜蜜点）、范围和数据集边界、以及
   局限性或未来工作说明。
4. **Pass D — 陷阱猎捕。** 对以下八类陷阱，判断论文是否存在风险，
   并用错误表述和正确表述同时记录：
   - `fabrication` — 幻灯片可能捏造论文中没有的内容（额外实验、
     部署声明、未做的比较）。
   - `metric_misread` — 容易混淆的指标（例如"指示热效率"vs
     "有效热效率"；"Shannon 多样性指数"vs"Simpson 指数"；
     "湿基含量"vs"干基含量"）。
   - `non_monotone_flattened` — 论文中的 U 型、倒 U 型或最优点
     关系，粗心的幻灯片可能简化为"越多越好"（例如压缩比-效率
     的甜蜜点、施肥量-产量的先增后减趋势）。
   - `condition_level_confusion` — 论文仔细区分的实验条件、处理
     方式或测量方法（例如"静态燃烧 vs 动态燃烧"、"间伐 vs
     皆伐"、"盆栽实验 vs 大田试验"、"单栏 vs 双栏排版"），
     粗心的幻灯片可能混淆。
   - `scope_overclaim` — 论文在特定条件下证明的结论（单一树种、
     特定区域、特定燃料类型、仿真环境），幻灯片可能过度泛化。
   - `unit_or_definition_error` — 容易用错单位或定义的数量（kW
     vs kJ、ppm vs mg/m³、绝对湿度 vs 相对湿度、干基 vs 湿基）。
   - `trend_direction_error` — "降低/升高/增加/减少"等趋势方向
     表述，粗心的幻灯片可能弄反。
   - `factor_misattribution` — 论文将某效果归因于特定实验因素
    （施肥处理、喷油正时、间伐强度），粗心的幻灯片可能归因于
     错误因素或整体系统。

## 填写 Paper Card

Schema 是合同。写任何内容之前先阅读它。几个关键澄清：

- `central_thesis`：一句话，捕获**问题 + 方法 + 核心发现/权衡**。
  避免"研究了"、"探讨了"、"分析了"等模糊动词。使用中文。
- `page_count_range`：根据论文正文页数确定：
  - 8-9 页正文 → `[10, 14]`
  - 10-12 页正文 → `[12, 16]`
  - 13-15 页正文 → `[14, 18]`
  - 16+ 页正文 → `[16, 20]`
- `conference`：从论文页眉、页脚或标题页提取完整会议名称和年份。
  常见值：中国林业学术大会、交通能源与智能动力大会(CTEIP)、
  内燃机高效低碳清洁燃烧学术年会、中国林业青年学术年会、
  中国农学会全国代表大会、设计与智能制造学术年会、
  全国炼钢学术会议、中国森林保护学术大会。
- `domain`：填写主要研究领域，例如"内燃机/燃烧"、"森林生态"、
  "土壤/水土保持"、"经济/政策"、"农业/农学"等。
- `paper_type`：根据论文研究方法判断：
  - `experimental`：有实验设计、对照组、定量测量结果
  - `computational`：以数值模拟/仿真为主（CFD、有限元等）
  - `qualitative`：历史研究、政策分析、案例研究，以定性论述为主
  - `review`：文献综述、研究现状分析
  - `mixed`：兼具定量实验和定性分析
- `ordered_sections`：≥10 条，≤14 条，按此规范顺序排列（可省略
  `limitations` 或 `visual_analysis` 如果论文不适用）：
  1. `title`
  2. `outline`
  3. `background`
  4. `limitations`（现有方法/研究的不足；可选）
  5. `method_overview`
  6. `methodology`
  7. `key_procedure`（关键实验程序/技术路线/分析方法；可与
     `methodology` 合并，但若合并须将 kind 标为 `key_procedure`）
  8. `materials_and_data`（试验材料与数据）
  9. `setup`（实验设置/条件）
  10. `results`
  11. `visual_analysis`（可选——定性样本、消融图、微观图像）
  12. `takeaways_limitations`
  13. `conclusion`
- 标题页（kind: `title`）的 `bullets` 必须恰好四条，格式为：
  - `论文标题: <完整标题>`
  - `作者团队: <作者>`
  - `单位: <单位>`
  - `会议: <完整会议名 + 年份>`
- 大纲页（kind: `outline`）的 `bullets` 为 `[]`。
- 其他所有章节，给出 2-5 条要点，采用 `标签: 定性描述` 格式，
  每条 ≤ 30 字。要点描述**该页幻灯片应涵盖什么主题**和**应突出
  的定性视角**。要点须在主题/机制/数据集/基线名称层面论文特定化
 （不可原封不动换到另一篇论文），但**不得**预泄露具体数值、
  精度百分比、`+/-Δ` 增益——这些是幻灯片生成模型应从 PDF 中
  提取并获得评分的答案。

  **好的要点示例**——描述范围（要涵盖的主题、比较结构）：
  - `核心方法：采用预燃室湍流射流点火技术实现氨燃料的稳定着火与燃烧。`
  - `实验设计：描述不同压缩比和当量比条件下的燃烧特性对比方案。`
  - `样地设置：说明不同海拔梯度下的土壤采样方案与分析指标体系。`
  - `性能对比：对比不同喷油正时策略对发动机效率和排放的影响趋势。`
  - `品种比较：对比不同砧木嫁接组合对果实品质指标的影响趋势。`
  - `模型验证：描述仿真结果与实测数据的吻合程度评估方法。`

  **坏的要点示例**——答案形态（读者无需看 PDF 就能填入幻灯片）：
  - `指示热效率：压缩比15:1时达到46.2%，较12:1提高了3.8个百分点。` ← 具体数值
  - `Shannon指数：样地A为2.34，样地B为1.87，差异显著(P<0.05)。` ← 具体值 + 显著性
  - `排放对比：NOx降低了32.5%，碳烟降低了18.7%。` ← Δ 值
  - `土壤含水量在施肥处理后从12.3%升至18.7%。` ← 具体参数

  区别是结构性的。好的要点表述*应涵盖什么*（趋势、比较、
  方法），坏的要点表述*应说什么*（具体数值、排名、Δ 值）。

- kind 为 `methodology`、`key_procedure`、`results`、
  `visual_analysis` 和 `limitations` 的章节**应当**包含
  `design_constraint`。`design_constraint` 必须引用你在 PDF 中
  确实看到的图/表标识符，描述**该图/表涵盖什么主题**，不涉及
  具体数值。

  好：`展示燃烧过程示意图（参见图2），显示预燃室射流点火的工作机理。`
  好：`包含实验结果对比表（参见表1和表2），涵盖不同工况下的性能对比。`
  坏：`引用表4展示压缩比15:1时46.2%的指示热效率。` ← 含具体值
  坏：`展示图3中NOx降低32.5%的结果。` ← 含具体值

- `key_numbers` ≥ 6 条。每个 `claim` 是"数值 + 单位 + 条件"的
  完整锚点，使用中文。
- `key_figures` ≥ 4 条。使用论文的精确标识符格式（`图1` 或
  `Fig. 1`）。
- `key_terms` ≥ 5 条。每个给出幻灯片必须遵守的一句话定义。如果
  粗心的幻灯片可能混淆，填写 `common_confusion`。使用中文。
- `traps` ≥ 4 条。尽量使用不同的 `kind` 值，为 Stage 3 提供
  足够的区分性评分材料。使用中文。

## 反预泄露（关键）— 三项原则

幻灯片生成模型只会看到渲染后的 `instructions.md`，永远看不到
Paper Card。三项原则确保范围内容和答案内容清晰分离。

### 原则 1 — 不相交集合

Paper Card 的字段按设计分为两个角色：

- **范围字段** — `ordered_sections[*].bullets` 和
  `ordered_sections[*].design_constraint`。流入 `instructions.md`。
- **答案字段** — `key_numbers[*].claim`、
  `key_terms[*].definition`、`traps[*].correct_form` 和
  `key_figures` 引用的数值。仅流入 Stage 3 评分标准，是**评分密钥**。

两者必须在内容层面不相交。

### 原则 2 — 范围形态，非答案形态

每条要点描述**该页幻灯片应涵盖什么**——要回答的问题、要做的
比较、要涵盖的主题——而非**幻灯片将说什么**。判断标准是机械的：

> 仅读要点、不打开 PDF 的人，能否写出幻灯片的定量结论、
> 参数值、显著性水平或正确措辞？

如果能，该要点就是答案形态，必须改写。

### 原则 3 — 写入前的镜像检查

在输出 `_paper_card.json` 之前，逐条检查每个 bullet 和每个
`design_constraint`，问四个问题：

1. 是否包含数字标记（数值+单位、%、×、比值、样本量、运行时间、
   P值）且同时出现或可改写为 `key_numbers[*].claim`？若是，
   移除数值——保留主题框架，删除具体值。
2. 是否表述了与 `key_terms[*].definition` 或
   `traps[*].correct_form` 重叠的定义/正确措辞？若是，替换为
   对*该类事实*的引用。
3. 是否包含与 `key_numbers` 条目重叠的参数值、样本量、实验条件
   常数？若是，抽象化为范围形态框架。
4. **（独立于答案字段。）** 是否包含**实验参数**（压缩比15:1、
   转速1500r/min、施肥量200kg/hm²）、**统计量**
  （P<0.05、R²=0.89）或公式表达式？这些都是幻灯片应从论文中
   读取的答案，即使不在 `key_numbers` 中也是如此。

## 自完善检查（写入 _paper_card.json 前）

在所有 `ordered_section` 的要点草拟完成后，执行一次**自完善检查**：

1. **统计 Section 1 的总要点数**，排除标题页的四个固定字段和大纲
   页的空数组。
2. **目标总数：30-40 条。** 官方 PPTSynth 学术任务集中在此
   范围。各章节的数量不必均匀——方法论、结果可以有 4-5 条，
   数据/结论/背景通常 2-3 条即可。
3. **若总数 > 40，修剪**低价值要点。优先删除：重述同章节其他要点
   的、描述子细节而非幻灯片级主题的、填充性语言的。
4. **优先删除而非合并。**
5. **若总数 < 30**，在最核心章节（方法论、结果、关键实验程序）
   补充要点。新要点必须遵守反预泄露规则。

## 反面目标

- 不要把摘要复述回去。
- `key_numbers` 中不要用 "≈X%" 这样的占位值。填真实数字。
- 要点不能读起来像教科书（"定义土壤理化性质"）。要点必须在主题
  层面特定于*这篇*论文。

## 最终响应

在用 Write 工具将 JSON 写入 `_paper_card.json` 后，**仅**输出
该 JSON 对象作为最终助手消息。无 markdown 围栏，无文字说明。

**JSON 转义**：字符串值中若需引用中文引号，使用中文弯引号（""）
而非 ASCII 双引号。若确实需要 ASCII 双引号，必须用 `\"` 转义。
示例：`"日军实施"三光"政策"` ✓，`"日军实施\"三光\"政策"` ✓，
`"日军实施"三光"政策"` ✗（破坏 JSON 结构）。

**不要运行验证命令。** 不要调用 Bash 或 Python 检查 JSON、计数
或重新读取已写内容。管线在本阶段结束后会严格校验；冗余检查只会
浪费回合数。一次彻底阅读 PDF、一次 Write JSON、一条最终消息
——这就是整个阶段。
