# Stage 3: 编写评判评分标准

你的任务：生成一个 JSON 文件 `generation_task/judge_prompt.json`，
包含两组二元评分检查项，风格与 PPTSynth 学术检查列表完全一致。
文件中不放其他内容。两个前缀（`material_dependent_prefix`）和
逐页保真度检查列表由评估框架后期追加。

## 输入

- `_paper_card.json` — 验证通过的 Paper Card。
- `_field_manifest.txt` — 自动生成的必覆盖清单，列出本论文的
  全部 key_number、trap 和易混淆 key_term。**你必须覆盖清单中
  列出的每一条。**
- `generation_task/instructions.md` — 渲染后的任务指令。每个
  完整性检查项必须对应 `instructions.md` 中要求包含的内容。

## 输出格式

文件是一个仅含两个键的 JSON 对象：

```json
{
  "material_dependent_checklist_1": [...],
  "material_dependent_checklist_2": [...]
}
```

- `material_dependent_checklist_1` — **内容完整性**（C1）。
- `material_dependent_checklist_2` — **内容正确性**（C2）。

不含其他键。不含前缀。不含注释。

## 检查项格式（严格匹配官方格式）

每个检查项是一个 Markdown 风格的字符串。完整性项的格式：

```
\n**<二元判断问题>？**\n\n  注意：您只需检查幻灯片是否包含所需内容，无需验证其正确性。\n  如果**否**，<描述缺失或不足之处>。\n
```

正确性项的格式：

```
\n**<带具体锚点的二元判断问题>？**\n\n  如果**否**，<列出具体差异>。\n
```

结构细节：
- 每个字符串以 `\n` 开头和结尾。
- 问题用 `**...**` 包裹，以 `？` 结尾。
- 完整性项包含"注意："行，正确性项不含。
- "如果**否**，……" 须针对具体检查项。

## 内容规则

### 完整性检查列表（C1）

#### 固定必需项（恰好 3 项）：
1. 标题页包含标题、作者和会议/单位。
2. 结论或总结页。
3. 局限性或未来工作。

#### 论文特定项：
按 `ordered_sections` 中的各个不同内容块，每块生成一项。
检查项数量由论文内容驱动——**不要**强制固定数量。
使用 `_field_manifest.txt` 中的建议数量作为参考，但让论文结构
决定实际数量。典型范围：总计 10-16 项（3 项固定必需 + 7-13 项
论文特定）。

论文特定完整性项规则：
- 使用 `key_terms` 中的论文原有术语（不用泛化的"该方法"）。
- 描述图/表的**内容**，而非编号："展示 X 与 Y 在数据集 Z 上
  对比的柱状图"而非"图 3"。
- 每项测试**一个**概念——将多部分章节拆分为单独检查项。
- 每项**必须**引用论文特定实体。对任何论文都相同的项是被禁止的。

#### 建议功能类型（参考使用，不适用可跳过，需要可增加）：
- 背景/研究动机页，指出现有工作的不足
- 核心概念定义（使用 `key_terms` 中的实际术语）
- 方法/实验程序概述，含命名的步骤、模块或指标
- 使用的数据集/试验材料（引用实际名称）
- 含命名基线/对照组的实验设置
- 定量结果（从 `key_numbers` 中取值）
- 定性或视觉分析结果
- 消融/敏感性分析（若论文有）

### 正确性检查列表（C2）

#### 建议功能类型（参考使用，不适用可跳过，需要可增加）：
- **定义准确性**：有 common_confusion 的 key_terms——
  "X 是否正确定义为……而非……？"
- **技术路线归因**：condition_level_confusion 类型的 traps
- **核心方法机制**：key_terms[0-1].definition
- **定量数据一致**：嵌入 ≥2 个 key_numbers 的数值+单位+条件
- **概念区分**：最易混淆的概念对
- **指标定义**：实际指标名称和公式
- **反捏造**：fabrication 类型的 traps，用"X 而非 Y"格式
- **观察性发现**：论文中的特定定性结果
- **配置准确性**：实验材料/设备/预处理细节
- **数据归属**：每个引用数值的来源

#### 必覆盖规则：
- 你**必须**在正确性检查项中引用所有 key_numbers 条目。
  每个 key_number 至少作为一个检查项的具体锚点出现。
- 你**必须**为每个 traps 条目创建至少一个检查项。使用 trap 的
  `correct_form` 作为正确答案，`claim_to_avoid` 作为错误替代。
  格式："正确描述为 X，而非 Y"或"X 而非 Y"。
- 你**必须**为每个有 `common_confusion` 的 key_terms 条目
  创建一个检查项。该项应测试术语是否被正确定义（vs 错误的
  混淆替代）。

#### 对比锚点规则：
每个正确性检查项**应当**尽可能使用对比格式：
"X 而非 Y"、"正确描述为 X，而非 Y"、"采用 X 方法，
而非 Y"。其中 Y 通常来自 `traps[*].claim_to_avoid` 或
`key_terms[*].common_confusion`。
这使检查项具有最大区分力——正确的幻灯片会通过，而犯了
常见错误的幻灯片会失败。

## 原子性原则

每个检查项测试**恰好一个**二元条件。如果你发现自己在写
"A、B 和 C"且每个都可以独立判断是/否，请拆分为单独检查项。
唯一的例外是各组件构成一个不可分割的单一机制（例如函数的
"输入-输出对"）。

## 长度控制

- 问题部分：≤250 字符。
- "如果否"从句：≤150 字符。
- 总检查项：≤400 字符（嵌入 key_numbers 数据表的项可达 500
  字符）。

## 图/表引用规则

描述**内容**，而非编号。写"展示 X 与 Y 在数据集 Z 上对比
的柱状图"而非"图 3"。写"展示去除组件 A 效果的消融表"
而非"表 2"。生成的 PPT 不会保留论文的图表编号，所以基于
编号的引用使检查项无法评判。

## 模板化抑制

每个 material_dependent 检查项**必须**引用论文特定实体
（命名的方法、数据集、指标、模型或本论文独有的发现）。
对任何论文都相同的检查项——如"幻灯片是否包含清晰的
结论？"而不说明结论应包含什么——在论文特定位置是被禁止的。
（3 项固定必需完整性项是唯一例外。）

## 风格示例（学习**风格**，不要复制内容）

### 示例 A — 正确性检查项（实验类论文）：

```
\n**Plücker 坐标的描述是否准确？（例如，正确地将其定义为表示三维空间中直线的 6D 向量。）**\n\n  如果**否**，解释描述中与论文不一致之处。\n
```

```
\n**技术路线是否正确呈现为"分布式表示"而非"全局矩阵回归"？**\n\n  如果**否**，描述技术细节的偏差。\n
```

```
\n**"实验结果"中的性能数据是否与论文表格一致？（例如，CO3D 数据集上的旋转精度和相机中心误差率。）**\n\n  如果**否**，列出幻灯片与论文之间的具体差异。\n
```

### 示例 B — 完整性检查项：

```
\n**第一页幻灯片是否正确列出了标题、作者和单位？**\n\n  注意：您只需检查幻灯片是否包含所需内容，无需验证其正确性。\n  如果**否**，描述第一页缺失的内容。\n
```

```
\n**是否有一页幻灯片解释了"预燃室湍流射流点火"作为研究动机的核心概念？**\n\n  注意：您只需检查幻灯片是否包含所需内容，无需验证其正确性。\n  如果**否**，解释概念背景说明不足之处。\n
```

从这些示例中注意：
- 检查项**简短**（问题部分 120-250 字符）。
- 锚点具体且论文特定。
- "而非"模式自然出现在对比项中。
- 无图表编号——仅内容描述。

## 锚点规则

每个正确性项必须包含至少一个具体锚点：命名的术语、带条件的
数值、指标定义或区分对（X vs Y）。仅说"结果是否正确"而无
锚点是不允许的。

每个完整性项应使用论文特定的术语，而非泛化占位符。优先使用
"*预燃室湍流射流点火*技术"而非"所提方法"。

## 卫生规则

- 使用中文（英文术语保持原文）。
- 检查项中不写 `PPTSynth` 或 `自查`。
- 不得有两个检查项用不同措辞问同一个问题。

## 输出纪律

先用 Write 写入 `generation_task/judge_prompt.json`。然后
在最终助手消息中输出一个简短的 JSON 对象：

```json
{
  "stage": "rubric",
  "ok": true,
  "completeness_count": <int>,
  "correctness_count": <int>,
  "anchors_extracted_from_paper_card": <int>,
  "key_numbers_covered": <int>,
  "traps_covered": <int>,
  "confusable_terms_covered": <int>,
  "warnings": []
}
```

无其他文字、无代码围栏。
