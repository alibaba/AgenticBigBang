# Stage 3: 撰写评分标准（Judge Rubric）

你的任务：生成一个 JSON 文件
`generation_task/judge_prompt.json`，包含两个二元评分标准检查列表，
风格上与官方 PPTSynth 中文检查列表完全一致。
文件中不得包含其他任何内容。

## 输入

- `_doc_card.json`（或 `_paper_card.json`）— 验证通过的 DocCard。
- `generation_task/instructions.md` — 已渲染的任务指令。每个完整性
  检查项必须对应 `instructions.md` 中明确要求的内容。
- `_field_manifest.txt` — **自动生成的强制覆盖清单**，列出所有
  `key_number`、`trap` 和有 `common_confusion` 的 `key_term`。
  **你必须覆盖清单中的每一条。**

## 输出格式

文件是一个 JSON 对象，**仅**包含以下两个键：

```json
{
  "material_dependent_checklist_1": [ "<string>", "<string>", ... ],
  "material_dependent_checklist_2": [ "<string>", "<string>", ... ]
}
```

> **JSON 转义规则（非常重要）**：每个检查项是 JSON 字符串值。
> 若检查项文本内需引用具体内容（如文档中的例句或数值），
> **绝对不能**在 JSON 字符串中直接使用 ASCII 半角引号 `"`——
> 那会破坏 JSON 语法！正确做法：使用中文书名号 `「」` 或
> 直接删除引号，例如：`**示例「带领10人优化流程，节省300万美元」的人数…**`
> 而不是 `**示例"带领10人优化流程，节省300万美元"的人数…**`。

- `material_dependent_checklist_1` — **内容完整性**（C1）。
- `material_dependent_checklist_2` — **内容正确性**（C2）。

无其他键。无前缀。无注释。

## 检查项风格（严格匹配官方格式）

完整性检查项的格式：

```
\n**<二元问句>？**\n\n  注意：您只需检查幻灯片是否包含所需内容，无需验证其正确性。\n  如果**否**，<描述缺失内容>。\n
```

正确性检查项的格式：

```
\n**<带有具体锚点的二元问句>？**\n\n  如果**否**，<描述要指出的差异或错误>。\n
```

注意结构细节：
- 每个字符串以 `\n` 开头，以 `\n` 结尾。
- 问句用 `**...**` 包裹，以 `？` 或 `?` 结尾。
- 完整性项有 "注意：" 行（逐字如上）。
- 正确性项没有 "注意：" 行——仅有问句和 "如果**否**，…" 指令。
- "如果**否**，…" 必须是具体的，告诉评判模型否定时应指向什么。

## 内容规则

### 完整性检查列表（C1）

#### 固定必需项（正好 3 条）：
1. 标题页是否包含文档标题、作者/主讲人和来源单位/场合。
2. 是否有结论或总结页。
3. 是否提及局限性、风险或后续工作/计划。

#### 文档特定项：
对 `ordered_sections` 中每个**独立的内容模块**生成一个检查项。
项数由文档内容驱动——不强制固定数量。以 `_field_manifest.txt`
中的建议数量为参考，让文档的结构决定实际数量。
典型范围：10-16 条（3 条固定 + 7-13 条文档特定）。

文档特定完整性项的规则：
- 使用 DocCard 的 `key_terms` 中的术语（而非泛指"该方法"）。
- 描述图/表的**内容**，而非编号："对比 X 和 Y 指标的柱状图"
  而非"图3"。
- 每项测试**一个**概念——对多部分章节拆分为独立项。
- 每项必须引用文档特定实体。对任何文档都通用的项禁止出现。

#### 按文档类型的建议完整性项类型（参考，按实际内容取舍）：
- 背景/动机（识别现有问题或痛点）
- 核心概念/方法/产品定义（使用 `key_terms` 中的实际术语）
- 核心数据/指标（从 `key_numbers` 中引用一个数值的话题）
- 关键流程/步骤（引用实际步骤名称）
- 案例/实例（引用实际案例名称）
- 定量结果/KPI（从 `key_numbers` 引用）
- 视觉分析结果（引用 `key_figures` 中图表的内容）
- 问题与建议（如文档有专门章节）

### 正确性检查列表（C2）

#### 建议功能类型（参考，按实际内容取舍）：
- **定义准确性**：有 `common_confusion` 的 `key_terms`——"X 是否被
  正确定义为……而非……？"
- **流程/方法辨别**：`condition_level_confusion` 类型的 traps
- **核心数值匹配**：至少嵌入 2 个来自 `key_numbers` 的数值
  （数值+单位+条件）
- **概念区分**：最容易混淆的概念对
- **指标/单位定义**：实际指标名称和单位
- **反捏造**：`fabrication` 类型的 traps，使用"X 而非 Y"格式
- **趋势/方向准确性**：`trend_direction_error` 类型的 traps
- **范围声明准确性**：`scope_overclaim` 类型的 traps
- **数据归因**：每个引用数字的来源

#### 强制覆盖规则：
- **必须在正确性项中引用所有 `key_numbers` 条目。**
  每个 key_number 应作为具体锚点出现在至少一项中。
- **必须为每个 `traps` 条目创建至少一项。** 使用 trap 的
  `correct_form` 作为正确答案，`claim_to_avoid` 作为错误选项。
  格式："正确表述为 X，而非 Y" 或 "X 而非 Y"。
- **必须为每个有 `common_confusion` 的 `key_terms` 创建一项。**

#### 对比锚点规则：
每个正确性项应尽可能使用对比格式：
"X 而非 Y"、"正确表述为 X，而非 Y"，或"应描述为 X，而非 Y"。
Y 通常来自 `traps[*].claim_to_avoid` 或 `key_terms[*].common_confusion`。
这使检查项具有最强区分力。

## 原子性原则

每项测试**正好一个**二元条件。如果你发现自己在写"A、B 和 C"
（其中每个都可以独立判定是/否），请拆分为独立项。唯一例外是
当组成部分形成一个不可分割的单一机制时。

## 长度控制

- 问句部分：≤300 字符。
- "如果否" 子句：≤200 字符。
- 整项：≤550 字符（嵌入简短数据表的项可达 600 字符）。

## 图/表引用规则

描述**内容**，不引用编号。写"对比 X 和 Y 在 Z 条件下的柱状图"
而非"图3"。写"显示不同处理组疗效差异的汇总表"而非"表2"。
生成的幻灯片不一定保留原文档的图/表编号，基于编号的引用会使
检查项无法判断。

## 样式示例（学习**风格**，不要复制内容）

### 完整性项示例：

```
\n**幻灯片是否清楚地定义了"腹腔镜胆囊切除术"的核心操作步骤，包括关键解剖标志和切除流程？**\n\n  注意：您只需检查幻灯片是否包含所需内容，无需验证其正确性。\n  如果**否**，描述缺失或不充分之处。\n
```

```
\n**幻灯片是否展示了"供应链优化方案"的实施路线图，包括各阶段时间节点和关键里程碑？**\n\n  注意：您只需检查幻灯片是否包含所需内容，无需验证其正确性。\n  如果**否**，描述缺失或不充分之处。\n
```

### 正确性项示例：

```
\n**"治疗结果"部分的有效率数据是否与文档一致？（例如，腹腔镜组术后3天出院率达到92.5%，而非传统开腹组的78.3%。）**\n\n  如果**否**，列出幻灯片与文档之间的具体数值差异。\n
```

```
\n**幻灯片是否避免了将"碳中和"误表述为"碳减排"？（正确理解：碳中和指净零排放，需抵消全部剩余排放，而非仅减少排放量。）**\n\n  如果**否**，描述幻灯片中的错误表述。\n
```

```
\n**文档中第三季度GMV数据是否被准确引用为约1.2亿元，而非全年数据？**\n\n  如果**否**，指出幻灯片中引用的错误数值或时间范围。\n
```

## 禁止模式

以下格式的检查项会被审计评为低分，禁止使用：
- 对任何文档都通用的项（"幻灯片是否包含结论页？"）
- 同时测试存在性和正确性的混合项
- 引用图/表编号而非内容的项
- 每项包含 3 个以上独立条件的复合项
- 未引用任何文档特定实体的项
